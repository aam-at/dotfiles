# Theme generator

`generate.py` turns one canonical `palette.toml` into every application's
color config, so a palette edit propagates everywhere with:

```sh
python3 themes/generate.py themes/gruvbox-dark/palette.toml
python3 themes/generate.py themes/gruvbox-dark/palette.toml --check   # CI/pre-commit: fail on drift, write nothing
```

A pre-commit hook (`theme-generator-check`) runs `--check` against every
`themes/*/palette.toml` on each commit, so a hand-edit to a generated file
that isn't matched by re-running the generator gets caught before it lands.

## `palette.toml`'s schema

Deliberately small: `background`, `foreground`, `selection_background`,
`selection_foreground`, `cursor`, `cursor_text`, plus 8 `ansi.normal` and 8
`ansi.bright` colors. That's the full set of colors a theme author should
need to retune. A few fixed structural greys that apps ask for but that
aren't semantic accents (`NEUTRAL` in `generate.py`: `bg3`, `bg4`, `fg3`)
live as constants in the script instead of the schema — they're steps on
the neutral ramp, not something you'd want independent control over.

`check_contrast()` warns (doesn't fail) if `selection_background`/
`background` or `foreground`/`background` drop below a 3:1 contrast ratio.
That's deliberately narrow — it exists because a low-contrast
`selection_background` once shipped invisible in fzf; ANSI text colors
aren't checked, since a dim comment color is often intentional.

## Three ways a consumer gets wired in

Pick based on what the target file's format allows, not by app:

**1. Native import/include** (preferred, when the app supports it) — the
app's own config statically pulls in a generated file from
`~/.config/theme/<name>`, so `generate.py` never touches the app's config
file at all. Existing examples: `kitty.conf` (`include`), `alacritty.toml`
(`import`), `niri`'s `config.kdl` (`include`), `wezterm.lua`
(`dofile(...)`).

**2. Full generation** (`FULL_FILE_TARGETS` / `GENERATORS`) — for a file
that's *entirely* color values, `generate.py` reconstructs and overwrites
it wholesale from a template. Only safe when there's no static content a
hand-typed template could corrupt (see the yazi cautionary tale below).
Example: `general/x/Xresources`.

**3. Marker blocks** (`MARKER_FILES`) — for a file that mixes real
hand-maintained settings with a color block, wrap just the color lines in

```
# START_AUTOGENERATED_<NAME>
...
# END_AUTOGENERATED_<NAME>
```

(the comment syntax the file already uses — `#` works for TOML/YAML/shell,
adjust for other languages). `generate.py` replaces only the text between
the markers via `patch_markers()`; everything else in the file — keybinds,
menu layout, unrelated settings — is left untouched. `kitty.conf` uses this
for its tab-style block; `config/fish/config.fish`, `config/gitu/config.toml`,
`config/lazygit/config.yml`, `config/television/config.toml`, and
`config/tmux/tmux.conf.local` use it for their color sections.

Indentation note: `patch_markers()` preserves whatever whitespace precedes
the `# END_...` marker in the file, so nested contexts (e.g. a YAML key
under `theme:`) keep their indent. It can't fix indentation that's already
wrong in the file — if you hand-write a new marker pair, indent the `#
START_...`/`# END_...` lines and each body line the way the render
function's returned string expects.

## Cautionary tale: don't reconstruct a file with static content you can't perfectly retype

`config/yazi/theme.toml` mixes color values with nerd-font glyphs (private-use
Unicode) and long file-extension icon lists. The first attempt at wiring it
in used full generation (option 2) — reconstructing the whole ~300-line file
from an f-string template. It silently dropped several glyph characters that
didn't survive being retyped into Python source, and diff review caught it
only because the diff was suspiciously large. **`RECOLOR_FILES`** exists for
exactly this case: instead of regenerating the file, `recolor_yazi()` reads
the file's current text and swaps known current-hex-value → new-hex-value
pairs via a placeholder pass (so a new value can never collide with an old
one still waiting to be replaced). Every byte of static content — icons,
extension lists — is never touched, because it's never retyped.

Use this pattern (a `RECOLOR_FILES` entry) whenever a file needs full-file
color propagation but contains generated-content-adjacent static text you
can't confidently reproduce byte-for-byte from a template.

## Adding a new consumer

1. Figure out which of the three patterns fits the file's format and
   content (see above).
2. Write a `render_*`/`recolor_*` function in `generate.py` using `get(p,
   "role")` / `ansi(p, "normal"|"bright", "name")` for the palette lookups
   invoking `NEUTRAL[...]` only for the few structural greys.
3. Wire it into `GENERATORS`/`FULL_FILE_TARGETS`/`MARKER_FILES` as
   appropriate.
4. Run `python3 themes/generate.py themes/gruvbox-dark/palette.toml` and
   diff the result against what was there before — a large, unexpected diff
   on a file with static content is the yazi failure mode above; go back to
   `RECOLOR_FILES` instead of debugging the template.
5. Run `--check` again immediately after to confirm the generator is
   idempotent (a second run should report zero changes).

## Adding a new theme (not just editing this one)

`generate.py` takes any `palette.toml` path — it isn't hardcoded to
`gruvbox-dark`. Create `themes/<name>/palette.toml` following the same
schema, run the generator against it with `--output-dir themes/<name>`, and
the `theme-generator-check` pre-commit hook picks it up automatically (it
globs `themes/*/palette.toml`, nothing to configure). `FULL_FILE_TARGETS`
and `MARKER_FILES`, however, target fixed absolute paths (e.g.
`config/yazi/theme.toml`) — those apply only to whichever theme is
currently "active" outside `themes/`, so switching the active theme means
re-running the generator against the new palette, not just adding it.
