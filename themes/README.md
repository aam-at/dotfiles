# Theme generator

One `palette.toml` per theme. `generate.py` renders it into every app's color
config, so a palette edit propagates in one command.

```sh
python3 themes/generate.py themes/gruvbox-dark/palette.toml
python3 themes/generate.py themes/gruvbox-dark/palette.toml --check   # report drift, write nothing
```

The `theme-generator-check` pre-commit hook runs `--check` over every
`themes/*/palette.toml`. A hand-edit to a generated file fails the commit
unless the generator reproduces it.

## Adding a consumer

1. Pick a wiring pattern from the target file's format, not from the app.
2. Write `render_*` or `recolor_*` in `generate.py`. Read colors through
   `get(p, "role")` and `ansi(p, "normal"|"bright", "name")`. Reach for
   `NEUTRAL[...]` only for the structural greys.
3. Register the function in `GENERATORS`, `FULL_FILE_TARGETS`, `MARKER_FILES`,
   or `RECOLOR_FILES`.
4. Run the generator and read the whole diff. Every changed line should be a
   color. A diff that touches anything else means the template is retyping
   static content: move the file to `RECOLOR_FILES` instead of debugging the
   template.
5. Run `--check`. It must report zero stale adapters, which is the only proof
   the generator is idempotent.

## Wiring patterns

Choose by what the target file's format allows.

**Native import.** The app's own config pulls a generated file out of
`~/.config/theme/<name>`, and `generate.py` never touches the app's config at
all. Use it wherever the app supports it: `kitty.conf` (`include`),
`alacritty.toml` (`import`), niri's `config.kdl` (`include`), `wezterm.lua`
(`dofile(...)`).

**Full generation** (`GENERATORS`, `FULL_FILE_TARGETS`). The generator rebuilds
the whole file from a template. Safe only when the file holds nothing but color
values, like `general/x/Xresources`.

**Marker blocks** (`MARKER_FILES`). For a file that mixes hand-maintained
settings with colors, wrap the color lines:

```
# START_AUTOGENERATED_<NAME>
...
# END_AUTOGENERATED_<NAME>
```

`patch_markers()` replaces only the text between the markers and leaves
keybinds, menu layout, and unrelated settings alone. Use the comment syntax the
file already has; `#` covers TOML, YAML, and shell. `kitty.conf` marks its
tab-style block this way, and `config/fish/config.fish`,
`config/gitu/config.toml`, `config/lazygit/config.yml`,
`config/television/config.toml`, and `config/tmux/tmux.conf.local` mark their
color sections.

`patch_markers()` copies the whitespace in front of the `# END_...` marker, so
a block nested under a YAML key keeps its indent. It cannot repair indentation
that is already wrong. When you hand-write a new marker pair, indent both
marker lines and every body line to match what the render function returns.

**Recolor** (`RECOLOR_FILES`) is the fourth pattern, below.

## Recolor files you cannot retype

`config/yazi/theme.toml` mixes colors with nerd-font glyphs from the Unicode
private-use area and long file-extension icon lists. Wiring it in through full
generation dropped several of those glyphs, which did not survive being retyped
into Python source. Review caught it only because the diff was suspiciously
large.

`recolor_yazi()` reads the file's current text and swaps old hex for new
through a placeholder pass, so a new value never collides with an old one still
waiting its turn. Static content survives because nothing retypes it. Use
`RECOLOR_FILES` for any file whose colors are threaded through text you cannot
reproduce byte for byte.

## palette.toml schema

`background`, `foreground`, `selection_background`, `selection_foreground`,
`cursor`, `cursor_text`, plus 8 `ansi.normal` and 8 `ansi.bright` colors. That
is the whole set a theme author retunes. Three structural greys that apps ask
for (`bg3`, `bg4`, `fg3`) sit in `NEUTRAL` in the script instead, since they
are steps on the neutral ramp rather than accents worth independent control.

`check_contrast()` warns without failing when `selection_background` or
`foreground` falls below 3:1 against `background`. It stays narrow on purpose.
A 1.7:1 `selection_background` once shipped invisible in fzf, while a dim ANSI
comment color is usually deliberate, so ANSI colors go unchecked.

## GTK: the theme reads the palette, not the app

Every other consumer reads its own config. A GTK app takes whatever the active
theme hands it, and themes differ in how much of that a palette can reach.
Stock Adwaita's compiled GTK3 stylesheet defines 36 `@define-color` names,
references one of them, and paints the other 788 colors from literal hex.
Overriding color names in `~/.config/gtk-3.0/gtk.css` recolors almost nothing
there. `adw-gtk3` (Arch package `adw-gtk-theme`, already in `install_arch.sh`)
inverts the ratio, roughly 1200 color-name references against 130 literal hex,
so the generated definitions reach every widget.

`render_gtk()` writes libadwaita's color vocabulary: surfaces
(`window_bg_color`, `view_bg_color`, `headerbar_bg_color`, `sidebar_*`,
`card_*`, `popover_*`, `dialog_*`), semantic accents (`accent_*`,
`destructive_*`, `error_*`, `warning_*`, `success_*`), GTK3's legacy `theme_*`
and `insensitive_*` aliases, and GNOME's `blue_1..blue_5` palette scale.
Adwaita apps hardcode that scale for chips and tags, which is what makes an
otherwise-themed app sprout stock GNOME blue. The GTK4 adapter writes every
value twice, once as `@define-color` and once as the `:root {
--window-bg-color: ... }` custom properties libadwaita 1.6+ reads. A single
selector rule survives, `caret-color`, which has no named-color hook. Anything
past that fights the theme instead of configuring it.

### dconf decides, settings.ini does not

`gtk-3.0-settings.ini` loses to `org.gnome.desktop.interface` whenever a
settings portal runs, which is every Wayland session here. So `generate.py`
writes `dconf.ini` from the same palette (`is_dark()` picks `adw-gtk3-dark` or
`adw-gtk3`), and `install.conf.yaml` pushes it with `dconf load
/org/gnome/desktop/interface/`. Two copies, one source, no drift.

This already bit once. dconf named `adw-gtk3-dark` while the package sat
uninstalled. A missing GTK3 theme name falls back to light Adwaita rather than
to the dark variant, and `prefer-dark` does not rescue it, so file dialogs came
up as beige Adwaita chrome with a stock blue Save button and gruvbox text.
Nothing warns. Check that the theme dconf names exists on disk:

```sh
ls -d "/usr/share/themes/$(gsettings get org.gnome.desktop.interface gtk-theme | tr -d \"\')"
```

`No such file or directory` is the whole bug.

`ICON_THEME` and `CURSOR_THEME` are hand-edited constants in `generate.py`
rather than palette keys, because settings.ini and dconf both have to name
them, and letting the two copies disagree is how this drifted.

## Adding a theme

`generate.py` takes any `palette.toml` path. Create `themes/<name>/palette.toml`
against the schema above, run the generator with `--output-dir themes/<name>`,
and the pre-commit hook picks it up from its `themes/*/palette.toml` glob.

`FULL_FILE_TARGETS`, `MARKER_FILES`, and `RECOLOR_FILES` write to fixed paths
outside `themes/`, such as `config/yazi/theme.toml`. Those files hold whichever
palette ran last, so switching the active theme means re-running the generator
against the new palette, not just adding it.
